# Lab 02 — IPv4, CIDR, Subnetting: PC는 같은 네트워크인지 어떻게 판단할까?

> **목표:** IP/마스크의 비트 연산으로 네트워크 경계를 계산하고, 호스트가 목적지를 on-link로 판단할 때 ARP가 언제 발생하는지 직접 확인한다.  
> **현재 상태:** 문서 준비 완료 · 실습/시뮬레이션은 아직 수행·검증하지 않음 · `.pkt` 파일 없음.

- `IP AND Mask`로 목적지가 같은 로컬 네트워크인지 판단하는 원리를 설명한다.

- **한쪽 마스크가 다른 비대칭 사례**를 별도로 진단한다.

## 2. 핵심 이론 — 주소가 같아 보이는 것과 같은 네트워크인 것은 다르다

### CIDR와 마스크의 의미

- **IPv4**: 32비트 주소. 점으로 나누어 쓴 `192.168.10.10`은 실제로 8비트 숫자 네 개의 표현.
- **CIDR**: Classless Inter-Domain Routing. `/26`의 26은 **네트워크 prefix 비트 수**를 뜻한다. 나머지 6비트는 호스트 부분.
- **Subnet Mask**: prefix 26개 비트를 1, 이후 6비트를 0으로 표기해 `255.255.255.192`가 된다.
- **Network ID** = `IPv4 AND Mask` (각 비트가 둘 다 1일 때만 1).
- 일반적인 IPv4 서브넷에서 **브로드캐스트 주소**는 호스트 비트를 모두 1로 채운 주소.
- 호스트 비트가 `h`개면 총 주소는 `2^h`개. 전통적인 브로드캐스트형 LAN(/30까지)의 일반적인 사용 가능 호스트 주소는 `2^h - 2`개. **/31 포인트투포인트·/32 호스트 경로는 예외**이며 후속 개념으로만 소개한다.
- IP 주소가 서브넷 안에 있는지 보려면 **대상 IP를 내 인터페이스 마스크와 AND한 값**이 내 `IP AND Mask`와 같은지 비교한다. 실제 OS는 라우팅 테이블과 목적지에 가장 적합한 경로를 이용해 on-link 여부/다음 홉을 판단하므로, 이번 식은 **추가 경로가 없는 단일 NIC의 직접 연결 네트워크**를 위한 간단한 모델이다.

### 예제: `192.168.10.10/26`

```text
IPv4 마지막 옥텟     : 00001010 (10)
Mask 마지막 옥텟     : 11000000 (192)
AND 결과             : 00000000 (0)
Network              : 192.168.10.0/26
호스트 범위          : 192.168.10.1 - 192.168.10.62
Broadcast            : 192.168.10.63
다음 /26 Network     : 192.168.10.64/26
```

같은 /24 대역도 /26이면 네 개로 갈린다.

| Prefix | 네트워크 | 일반적인 사용 가능 호스트 | 브로드캐스트 |
| --- | --- | --- | --- |
| /26 | 192.168.10.0 | .1~.62 | .63 |
| /26 | 192.168.10.64 | .65~.126 | .127 |
| /26 | 192.168.10.128 | .129~.190 | .191 |
| /26 | 192.168.10.192 | .193~.254 | .255 |

`/24`는 `255.255.255.0`, 총 256개 주소/일반적 사용 가능 254개. `/26`은 `255.255.255.192`, 총 64개/62개. `/30`은 `255.255.255.252`, 총 4개/2개.

### PC가 실제로 판단하는 순서

1. 송신 호스트가 대상 IPv4와 자신의 라우팅 정보를 조회한다.
2. 직접 연결 경로(on-link)라고 판단하면 목적지 IPv4에 대응하는 MAC을 **ARP로 조회**하고 Ethernet 프레임을 보낸다.
3. 다른 네트워크라면 일치하는 경로의 **다음 홉**을 찾는다. 경로가 없다면 전송할 수 없다.
4. 다음 홉을 이용하는 경우 ARP는 최종 목적지가 아니라 **로컬 링크에 있는 다음 홉의 MAC**을 확인한다.
5. **주의:** 스위치는 IPv4 /26 계산을 대신해 주지 않는다. 스위치는 같은 VLAN 내 Ethernet 프레임을 전달할 뿐이다.

### 예상 질문

- `192.168.10.10/26`에서 `192.168.10.70`을 직접 ARP로 찾으려 할까?
- 같은 스위치인데 IP Ping이 안 되는 것이 왜 모순이 아닐까?
- `192.168.10.63/26`을 일반 PC 호스트 주소로 쓰면 왜 안 될까?

## 3. 토폴로지 및 주소 계획

기존 Lab 01처럼 2960 스위치 한 대와 PC **세 대**로 시작한다. 케이블은 모두 Copper Straight-Through, 기본 VLAN 1. 라우터 없음.

```text
PC0 Fa0 --- Fa0/1 [Switch0 2960] Fa0/2 --- Fa0 PC1
                      |
                    Fa0/3
                      |
                    PC2 Fa0
```

| 장비 | IP 주소 | 마스크 | /26 Network | Gateway |
| --- | --- | --- | --- | --- |
| PC0 | 192.168.10.10 | 255.255.255.192 (/26) | 192.168.10.0/26 | 비움 |
| PC1 | 192.168.10.20 | 255.255.255.192 (/26) | 192.168.10.0/26 | 비움 |
| PC2 | 192.168.10.70 | 255.255.255.192 (/26) | 192.168.10.64/26 | 비움 |

예상: PC0 ↔ PC1 **성공**, PC0 ↔ PC2 **실패**. 스위치 포트가 이어져 있어도 PC0/PC2는 IP 관점에서 다른 네트워크다.

## 4. 실습 — 구축 (GPT는 각 단계별 실제 결과를 확인)

1. Packet Tracer에서 PC0/PC1/PC2와 2960 한 대를 배치하고 위 포트에 케이블 연결. 링크 녹색 확인.
2. 각 PC에서 **Desktop → IP Configuration**에 설계표 주소 및 마스크 입력, Default Gateway는 빈 값 유지.
3. PC0에서 `ipconfig`로 실제 주소·마스크 확인; PC1/PC2에서도 확인.
4. 계산 문제: PC0과 PC2의 Network ID를 직접 구해 예상 Ping 결과를 말로 설명한 뒤에 트래픽 생성.

> 사용자 실습을 통과하기 전 다음 순서를 한꺼번에 수행했다고 주장하지 않는다.

## 5. 정상/격리 검증과 패킷 관찰

PC0 **Desktop → Command Prompt**:

```text
ping 192.168.10.20
ping 192.168.10.70
arp -a
```

**기대값:** PC1은 응답, PC2는 응답 없음. 단, Packet Tracer의 `Request timed out` 문구 자체가 원인 증거가 되지는 않는다. ARP 캐시에는 PC1 주소가 생길 수 있지만, **PC2 목적지 IP를 직접 ARP한 엔트리**는 생성되지 않아야 한다(캐시를 지우고 본 실험을 실행했을 때).

Simulation Mode에서 ARP/ICMP 필터 활성화 → 캐시 제거(`arp -d`, 해당 Packet Tracer 환경에서 지원되는 경우) → PC1 Ping과 PC2 Ping을 **각각 독립적으로** 실행하여 이벤트 비교:

- PC1: 로컬 판단 → ARP Request(브로드캐스트) → ARP Reply(유니캐스트) → ICMP Echo Request/Reply.
- PC2: /26에서 비로컬 판단 → 기본 게이트웨이 부재 → 송신 측에서 폐기(이전 Lab의 내부 처리 메시지와 비교). PC2를 목적지로 하는 직접 ARP가 나오면 구성/필터/이벤트를 재검증.
- 필요시 Switch0에서 `enable`, `show mac address-table`로 MAC↔포트 학습 확인. **L2 테이블만으로 서로 다른 IP 네트워크 사이를 라우팅할 수 없음**에 주목.
- Simulation에서 나온 정확한 오류 메시지는 실행한 Packet Tracer 버전에 따라 다를 수 있으므로 실제 관찰 후 기록한다.

## 6. 오류 재현·진단·복구

### 필수 Case A — 서브넷 마스크 비대칭 (중요)

**정상 상태:** PC0 `192.168.10.10/26`, PC1 `192.168.10.20/26`, Ping 성공.

1. PC1만 `255.255.255.240 (/28)`으로 변경. PC1은 `192.168.10.16/28`에 속하고 PC0은 PC1을 자신의 `192.168.10.0/26` on-link로 본다.
2. PC0 → PC1 Ping을 시도한다. PC0은 PC1을 로컬로 보고 ARP/ICMP Echo Request를 보낼 수 있지만, **PC1은 PC0 `192.168.10.10`을 자신의 /28 밖으로 판단**하여 기본 게이트웨이 없이 Echo Reply를 돌려보낼 수 없다.
3. `ipconfig`, Simulation ARP/ICMP 이벤트를 통해 **요청의 왕복 중 어떤 방향이 실패했는지** 확인한다. Ping timeout만으로 ARP 실패라고 단정하지 않는다.
4. PC1 마스크를 `255.255.255.192`로 복구하고 Ping 성공 확인.

> PC0 `.10/26`과 PC1 `.20/28`의 비대칭 사례는 서로의 송수신 판단이 다르다는 것을 보여준다. PC1의 ARP/응답 동작은 Packet Tracer 구현에 따라 세부 표시가 달라질 수 있으므로 관찰값 기준으로 확인한다.

### 선택 Case B — 중복 IPv4

1. 정상 환경에서 PC2에 `192.168.10.20/26`을 일시적으로 설정하여 PC1과 충돌하게 만든다.
2. IP 중복 경고가 표시되는지와 ARP 매핑·Ping의 불안정 여부를 관찰한다. **반드시 통신 실패가 재현된다고 단정하지 않는다.** Packet Tracer 장비/버전에 따라 충돌 표시·반응이 다를 수 있다.
3. PC2를 `192.168.10.70/26`으로 복구하고 원래 통신/격리 결과를 재확인한다.

### 문제 해결 접근

`IP/Mask 확인 → Network ID 계산 → 송신/응답 방향 경로 판단 → ARP와 ICMP 이벤트 확인 → 복구 후 재검증`. 모든 트래픽이 실제 동일 브로드캐스트 도메인에 있을 수 있다는 사실과, **각 호스트의 L3 로컬 네트워크 판단**을 분리해 생각한다.

## 8. 핵심 3가지·다음 학습

- CIDR prefix는 네트워크 비트의 길이를 표현하며, 마스크와 AND하여 로컬 네트워크 경계를 이해할 수 있다.
- 물리적으로 동일 L2 스위치/VLAN에 연결되어 있어도 호스트가 IP 목적지를 off-link로 판단하면 라우팅 경로가 필요하다.
- 장애에서는 **송신 경로뿐 아니라 응답 경로도** 별도로 확인한다.
