# u5. Cooldown과 안정화

## 지도 확인

Auto Scaling은 너무 자주 Scale Out과 Scale In을 반복하면 오히려 불안정해질 수 있다.

예를 들어 CPU가 잠깐 높아졌다고 서버를 늘렸는데, 새 서버가 준비되기도 전에 또 CPU를 보고 추가 Scale Out하면 과도하게 서버가 늘어날 수 있다.

이런 급격한 반복 조정을 줄이기 위해 **Cooldown**이라는 개념이 등장한다.

---

## 1. Cooldown이란?

Cooldown은 Scaling Action이 발생한 뒤 **추가 Scaling Action을 잠시 기다리는 시간**이다.

강의에서는 기본값을 300초로 설명한다.

```text
Scale Out 발생
→ EC2 추가
→ Cooldown 시작
→ 잠시 추가 scaling 대기
→ metric 안정화 확인
```

핵심은 새 인스턴스가 실제로 부하를 받아 metric에 영향을 주기까지 시간이 필요하다는 점이다.

---

## 2. 왜 바로 다시 판단하면 안 되나?

예를 들어:

```text
현재 EC2 2대
평균 CPU 85%
```

그래서 EC2 2대를 추가했다고 하자.

```text
2대
→ Scale Out
→ 4대
```

하지만 새 EC2는 아직 다음 과정을 거칠 수 있다.

```text
부팅
→ 애플리케이션 시작
→ Health Check 통과
→ 요청 받기 시작
```

이 과정이 끝나기 전에 CPU를 다시 보면 기존 2대의 CPU는 여전히 높을 수 있다.

그 상태에서 또 Scale Out하면:

```text
4대가 막 준비 중인데
→ 또 2대 추가
→ 6대
```

처럼 필요 이상으로 늘어날 수 있다.

Cooldown은 이런 과잉 반응을 줄이는 완충 시간이다.

---

## 3. 안정화라는 관점

Scaling의 목적은 숫자를 자주 바꾸는 것이 아니라 **워크로드에 맞는 안정적인 크기로 수렴하는 것**이다.

따라서 Scaling Action 이후에는 새 상태가 metric에 반영될 시간을 줘야 한다.

```text
Scaling Action
→ 새 인스턴스 상태 반영
→ metric 변화
→ 다음 판단
```

이 흐름이 중요하다.

---

## 4. 준비가 빠른 AMI의 의미

강의에서는 준비된 AMI를 사용해 인스턴스 설정 시간을 줄이는 것이 도움이 된다고 설명한다.

예를 들어 User Data에서 매번 많은 패키지를 설치하고 애플리케이션을 구성하면 새 EC2가 실제 요청을 받기까지 오래 걸릴 수 있다.

```text
느린 시작
AMI 부팅
→ 패키지 설치
→ 앱 다운로드
→ 설정
→ 앱 시작
```

반면 필요한 소프트웨어가 이미 포함된 AMI라면:

```text
준비된 AMI
→ 부팅
→ 앱 시작
→ 빠르게 서비스 참여
```

처럼 준비 시간을 줄일 수 있다.

즉 **인스턴스가 빨리 준비될수록 Auto Scaling도 실제 부하 변화에 더 빠르게 대응하기 쉬워진다.**

---

## SAA 판단

```text
Scaling 직후 반복적인 추가 scaling을 잠시 막음
→ Cooldown

강의 기준 기본 cooldown
→ 300초

새 인스턴스 준비 시간이 너무 오래 걸림
→ 미리 준비된 AMI 활용 고려

Cooldown의 목적
→ metric과 새 capacity가 안정화될 시간 확보
```
