# INT-03 Linux 네트워크와 CNI

> 분류: **운영 심화** · 연결/선행: **04 시작 전** · [기본 학습](../../08-independent/README.md) · [환경 기준](../../07-cka-preview/ENVIRONMENT.md)

## Overview — 왜 배우는가?

netns, veth, routing, Pod CIDR와 CNI 구현별 차이를 이해한다. 기존의 관련 실습과 연결해, 객체 조회에 그치지 않고 **컴포넌트의 판단 → Linux/Runtime의 실행 → 상태·로그·이벤트 증거**를 이어서 설명한다.

## 선수 지식과 동작 원리

Node에서 ip 명령으로 실제 link/route를 관찰한다. 다른 Node의 Pod IP와 노드 라우팅을 비교한다. CNI에 따라 bridge, veth, overlay, BGP 또는 eBPF 구현이 다르다.

## 예측 후 관찰

실행 전에 (1) 예상 상태, (2) 이 상태를 책임지는 컴포넌트, (3) 검증할 증거를 먼저 적는다. 아래 명령은 Linux/bash 셸에서 실행한다. 리소스가 이미 만들어져 있어야 하는 명령은 연결된 이전 단계를 먼저 수행한다.

```bash
kubectl get nodes -o wide
kubectl get pods -A -o wide
ip -br addr
ip route
ip -br link
kubectl -n kube-system get ds
```

출력이 비어 있거나 오류가 나면 도구 부재·리소스 미준비·실제 장애를 구분한다. 비어 있는 값이나 실패를 정상 동작의 증거로 사용하지 않는다.

## 장애 가설 → 증거 → 복구

같은 노드/다른 노드 간 Pod IP 연결 실패를 구분한다. Node route·방화벽·CNI 데몬 로그와 Pod 상태를 증거로 활용한다.

가설과 관찰 결과가 일치하는지 기록하고, 최소한의 변경으로 복구한 뒤 **처음과 같은 명령/요청**으로 성공을 확인한다. 이 문서는 안전한 관찰 순서가 기본이며, 위험한 장애 주입은 명시한 별도 VM에서만 수행한다.

## 환경 제약 및 정리

호스트의 route, iptables, CNI 구성은 변경하지 않는다. 패킷 캡처는 선택.

- Kubernetes 1.27.2에서 실제 실행한 내용과 최신 버전의 공식 설명을 구분한다.
- 이 문서 작성만으로 사용자 VM 실행 완료를 뜻하지 않는다.
- 실습 완료 기록: [CHECKPOINTS](../../08-independent/CHECKPOINTS.md).
